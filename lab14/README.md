# Лабораторна робота №14 — Аналіз SRP/OCP у відкритих репозиторіях

**Тема:** Аналіз SRP/OCP у відкритих репозиторіях.

**Мета:** Навчитися знаходити приклади використання та порушення принципів SRP і OCP у реальних проєктах на C#.

---

## 1. Обрані репозиторії

Для аналізу я обрав два відкриті проєкти на GitHub:

1. **FluentValidation** — бібліотека для перевірки правильності введених даних.  
   Репозиторій: https://github.com/FluentValidation/FluentValidation

2. **MonoGame** — фреймворк для створення комп'ютерних ігор.  
   Репозиторій: https://github.com/MonoGame/MonoGame

---

## 2. Приклади правильного застосування SRP

**Приклад 1. FluentValidation — PredicateValidator**

Файл: [PredicateValidator.cs](https://github.com/FluentValidation/FluentValidation/blob/main/src/FluentValidation/Validators/PredicateValidator.cs)

Клас `PredicateValidator` відповідає за перевірку значення за заданою умовою. Він не займається збереженням даних або роботою з інтерфейсом.

Це відповідає SRP, оскільки клас має одну основну відповідальність. Якщо потрібно змінити спосіб перевірки, це не вплине на інші частини програми.

**Приклад 2. FluentValidation — PropertyRule**

Файл: [PropertyRule.cs](https://github.com/FluentValidation/FluentValidation/blob/main/src/FluentValidation/Internal/PropertyRule.cs)

Клас `PropertyRule` відповідає за виконання правил перевірки окремої властивості об'єкта.

Це хороший приклад SRP, тому що логіка перевірки властивості знаходиться в окремому класі. При додаванні нових правил не потрібно змінювати код інших компонентів системи.

---

## 3. Приклади можливого порушення SRP

**Приклад 1. MonoGame — Game**

Файл: [Game.cs](https://github.com/MonoGame/MonoGame/blob/develop/MonoGame.Framework/Game.cs)

Клас `Game` відповідає за запуск гри, оновлення ігрового стану, малювання, керування компонентами та взаємодію з графічною системою.

На мою думку, тут є ризик порушення SRP, оскільки клас виконує багато різних завдань. Через це зміни в одній частині можуть впливати на інші.

При додаванні нових можливостей клас може ставати складнішим для підтримки.

**Приклад 2. MonoGame — ContentManager**

Файл: [ContentManager.cs](https://github.com/MonoGame/MonoGame/blob/develop/MonoGame.Framework/Content/ContentManager.cs)

Клас `ContentManager` займається завантаженням ресурсів, їх збереженням у пам'яті та звільненням після використання.

Ці завдання пов'язані між собою, але їх можна розділити на окремі компоненти. Це могло б спростити підтримку коду.

Наприклад, при додаванні нового способу завантаження ресурсів доведеться перевіряти, чи не впливають зміни на керування пам'яттю.

---

## 4. Приклади застосування OCP

**Приклад 1. FluentValidation — AbstractValidator**

Файл: [AbstractValidator.cs](https://github.com/FluentValidation/FluentValidation/blob/main/src/FluentValidation/AbstractValidator.cs)

Клас `AbstractValidator<T>` дозволяє створювати власні перевірки, успадковуючи базовий клас.

Це відповідає принципу OCP, тому що можна додавати нові правила перевірки без зміни основного коду бібліотеки.

Наприклад, для перевірки нового типу даних достатньо створити окремий клас валідатора.

**Приклад 2. MonoGame — Game**

Файл: [Game.cs](https://github.com/MonoGame/MonoGame/blob/develop/MonoGame.Framework/Game.cs)

Клас `Game` має віртуальні методи, наприклад `Update()`, `Draw()` та `LoadContent()`, які можна перевизначати у власній грі.

Завдяки цьому розробник може додавати нову ігрову логіку без зміни вихідного коду MonoGame.

Це приклад OCP, оскільки функціональність розширюється через успадкування.

---

## 5. Пропозиція рефакторингу

Для покращення структури я пропоную розділити частину відповідальностей класу `ContentManager` у MonoGame.

Можна створити окремі компоненти:
- `ResourceLoader` — для завантаження ресурсів.
- `ResourceCache` — для зберігання вже завантажених ресурсів.
- `ResourceDisposer` — для звільнення пам'яті.

Тоді кожен компонент відповідатиме за своє завдання. Це спростить підтримку коду та додавання нових можливостей.

При цьому потрібно зберегти сумісність із наявними методами `ContentManager`.

## 6. Висновок

Під час виконання лабораторної роботи я проаналізував два відкриті проєкти на C#. Я знайшов приклади використання принципів SRP та OCP. Принцип SRP допомагає розділяти програму на класи з окремими відповідальностями. Це робить код зрозумілішим і полегшує його підтримку. Також я побачив, що великі класи можуть поєднувати декілька завдань, хоча це не завжди означає помилку. Принцип OCP дозволяє додавати нові можливості без зміни вже написаного коду. На мою думку, обидва принципи корисні для створення програм, які простіше змінювати та розширювати.
