# Самостійна робота №18

**Тема:** PLINQ: дослідження продуктивності та безпеки.



## Опис експерименту

Я створив проєкт IndependentWork12.

Для перевірки використав List<int> із 1 мільйоном і 10 мільйонами випадкових чисел. Числа генеруються в діапазоні від 1 до 1000000 через Random(42).

Обчислювальна операція — перевірка числа на простоту. Метод IsPrime перевіряє наявність дільників до квадратного кореня числа.

Обидва запити відбирають прості числа та знаходять їхню суму. У PLINQ додано AsParallel. Для суми використано long.

Час вимірюється через Stopwatch. Генерація чисел і виведення результатів у вимірювання не входять.

## Результати продуктивності

Результати одного запуску в режимі Release:

| Кількість елементів | LINQ, мс | PLINQ, мс |
|---|---|---|
| 1000000 | 223.77 | 54.55 |
| 10000000 | 1253.31 | 365.96 |

Суми, отримані через LINQ і PLINQ, збіглися для обох розмірів колекції.

У цьому запуску PLINQ був швидшим в обох тестах. Перевірки чисел незалежні одна від одної, тому їх можна виконувати паралельно.

Для невеликої колекції або простої операції PLINQ може бути повільнішим через витрати на розподіл роботи та об’єднання результатів.

Час залежить від процесора, доступних ядер, навантаження системи та JIT-компіляції. На іншому комп’ютері результати можуть відрізнятися.

## Проблема побічних ефектів

Я створив спільний лічильник, який збільшується всередині ForAll. Експеримент повторюється тричі.

Очікуваний результат кожного запуску — 1000000.

| Спроба | Без синхронізації | З Interlocked |
|---|---|---|
| 1 | 414925 | 1000000 |
| 2 | 325547 | 1000000 |
| 3 | 297639 | 1000000 |

Операція wrong++ складається з читання, збільшення та запису значення. Кілька потоків можуть прочитати однакове число й перезаписати зміни один одного. Через це частина збільшень втрачається.

Для виправлення я використав Interlocked.Increment(ref correct). Цей метод атомарно збільшує лічильник, тому всі оновлення враховуються.

WithDegreeOfParallelism(4) задає ступінь паралелізму для демонстрації.

Результат без синхронізації непередбачуваний. Навіть якщо окремий запуск випадково дав правильне число, код залишається непотокобезпечним.

## Висновок

PLINQ доцільно використовувати для великих колекцій зі складними незалежними обчисленнями. Його швидкість потрібно перевіряти вимірюваннями.

Зміна спільних змінних із паралельних лямбда-виразів потребує синхронізації. Для простого лічильника підходить Interlocked.Increment.
